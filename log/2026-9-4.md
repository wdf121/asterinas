# 2026-09-04 Device Mapper 系统验收收敛

## 阶段 1：收敛为六个 canonical suite

### 背景

旧 `myshell/` 下保留了按历史阶段拆分的 control ABI、raw linear/striped、基础 LVM2、cross-segment 和 reboot 入口。它们与当前验收职责重叠，且 runner 的旧 flag 不能直接说明 control-plane、dataplane、LVM2 topology 与 filesystem/reboot integration 的边界。

### 改动

- [run_dm_system_tests.sh](../myshell/run_dm_system_tests.sh) 只保留六个显式 suite：
  - `--control-plane`
  - `--dataplane`
  - `--lvm2-topology`
  - `--linear-integration`
  - `--striped-integration`
  - `--mixed-integration`
- 删除历史阶段性入口：
  - `myshell/dm_linear/run_control_abi_test.sh`
  - `myshell/dm_linear/run_cross_target_bio_regression.sh`
  - `myshell/dm_linear/run_lvm2_linear_cross_segment_test.sh`
  - `myshell/dm_linear/run_lvm2_linear_reboot_test.sh`
  - `myshell/dm_mixed/run_lvm2_linear_striped_mixed_reboot_test.sh`
  - `myshell/dm_striped/run_lvm2_striped_cross_segment_test.sh`
  - `myshell/dm_striped/run_lvm2_striped_reboot_test.sh`
  - `myshell/dm_striped/run_raw_striped_bio_test.sh`
  - `myshell/run_dm_dataplane_edge_test.sh`
  - `myshell/run_dmsetup_cli_semantics_test.sh`
  - `myshell/run_lvm2_cli_semantics_test.sh`
- 保留公共 harness、`myshell/ktest_crate.sh`、`myshell/br.sh` 和 Linux baseline 对照脚本；不修改 KVM、RELEASE、QEMU 或 NixOS boot protocol。

### 验证

  myshell/lib/dm_nixos_test.sh \
  myshell/run_dm_control_plane_test.sh \

## 阶段 2：公共 harness 的启动、生命周期和输入稳定性

### 背景

系统验收需要区分 guest 是否及时启动，与 guest 内 LVM2/ext2/reboot 工作是否在合理时间完成。dataplane 非对齐 striped 场景首次运行在 Step 5 后达到总 lifecycle timeout，必须先区分真实 DM I/O hang 与 guest 命令没有被串口完整接收。

### 改动

- [dm_nixos_test.sh](../myshell/lib/dm_nixos_test.sh) 将 guest shell-ready timeout 与完整生命周期 timeout 分离：
  - `GUEST_READY_TIMEOUT=40`：QEMU 启动到日志出现 `root@asterinas` 的硬上限；超时退出。
  - `GUEST_QEMU_TIMEOUT=180`：单个 guest 从启动到退出的总上限。
- 每个 guest 输出 started、ready、completed 的 ISO 时间与 elapsed marker。
- 增加 QEMU group cleanup 和 `dm_run_three_guest_test()`；linear/striped integration 使用三次 guest，mixed integration 使用两次 guest。
- guest script 默认逐行注入并以 `GUEST_INPUT_LINE_DELAY=0.01` 节流；`GUEST_INPUT_LINE_DELAY=0` 可显式关闭。

### 验证

dataplane 初次异常运行中，guest shell-ready 为 25 秒，但 Step 5 后在 180 秒 lifecycle 上限结束。为定位问题，增加 Step 5 operation marker 和 20 秒局部诊断 timeout；后续确认 mapper Write、Flush、mapper read 都完成，卡点是长 shell script 一次性写入 QEMU serial 后，后续命令没有到达 guest，而非 DM I/O 或 completion hang。默认逐行 10ms 节流后 dataplane 完整通过。

## 阶段 3：非对齐 striped BIO 的精确 ktest

### 背景

真实 dataplane 需要从 mapper sector 2 单次写入 12 sectors 到 `striped 2 4` table。该 I/O 逻辑范围为 `[2,14)`，必须拆成四个 child，且原始 BIO 只能在全部 child 完成后完成一次。

### 改动

- [bio.rs](../kernel/core/comps/block/src/bio.rs) 增加仅 ktest 使用的 `BioSegment::alloc_exact()`，用于分配精确 12-sector 测试 payload。
- [table.rs](../kernel/core/comps/device-mapper/src/table.rs) 增加 deferred recording backing mock，并新增 `splits_twelve_sector_write_across_four_striped_children`。
- ktest 断言四个 child 的 backing range 与 payload 长度分别为 2/4/4/2 sectors；前三个 child 乱序完成时原 BIO 仍 pending，最后一个完成后原 BIO 恰好完成一次。

### 验证

```bash
myshell/ktest_crate.sh \
  kernel/core/comps/device-mapper \
  aster_device_mapper::table::tests::splits_twelve_sector_write_across_four_striped_children
```

结果：`1 passed; 0 failed; 69 filtered out`，并输出 `All crates tested.`。

## 阶段 4：六套 NixOS 系统验收

### 背景

按照 runner 的 canonical suite 逐个串行运行，避免 QEMU/test image 锁冲突。

### 验证

```bash
GUEST_READY_TIMEOUT=40 GUEST_QEMU_TIMEOUT=180 \
  myshell/run_dm_system_tests.sh --control-plane
GUEST_READY_TIMEOUT=40 GUEST_QEMU_TIMEOUT=180 \
  myshell/run_dm_system_tests.sh --dataplane
GUEST_READY_TIMEOUT=40 GUEST_QEMU_TIMEOUT=180 \
  myshell/run_dm_system_tests.sh --lvm2-topology
GUEST_READY_TIMEOUT=40 GUEST_QEMU_TIMEOUT=180 \
  myshell/run_dm_system_tests.sh --linear-integration
GUEST_READY_TIMEOUT=40 GUEST_QEMU_TIMEOUT=180 \
  myshell/run_dm_system_tests.sh --striped-integration
GUEST_READY_TIMEOUT=40 GUEST_QEMU_TIMEOUT=180 \
  myshell/run_dm_system_tests.sh --mixed-integration
```

六个 suite 均输出其 guest/test/host pass marker 和 `HOST_PASS_DM_SYSTEM_TESTS <suite>`；所有实际 guest shell-ready 都不超过 40 秒，运行结束后未发现残留 QEMU。linear 与 striped integration 分别完成 first/second/third guest，mixed integration 完成 first/second guest。
