# 2026-9-9 Device Mapper 进度

## 1. 历史实现：首次 resume 可操作发布

> 以下记录的是本日较早采用的 alias-first/primary-last 方案；它已在第 2 节被本机 Linux 基线驱动的 load/resume 生命周期对齐替代。

### 背景

首次 `dmsetup resume` 原先在 mapper block registry、VFS open gate 与 `/dev/dm-X`、`/dev/mapper/<name>` 已发布后，才将 inactive table 激活。路径可操作时仍可能没有 active table，BIO 会被拒绝。

### 改动

- `DmDevice` 增加 `InitialResumeGuard` 和 `begin_initial_resume()`：首次激活把同一张 inactive `Arc<DmTable>` 暂时移至 active；未 commit 的 guard 会恢复 table 与原 phase。
- control ioctl 的首次 resume 在 runtime 发布前创建 guard；已发布 mapper 的后续 resume 继续使用普通 `DmDevice::resume()`。
- mapper runtime 注册顺序调整为：Pending `RegisteredBlockDevice`、pending `BlockFile`、悬空 alias、block registry Live、open gate、最后创建 `/dev/dm-X`。
- `/dev/dm-X` 成为可操作发布点；它出现时 active table、Live registry 和 VFS open gate 已全部就绪，既有 alias 也可随之跟随。
- control-plane guest 脚本新增 `create --notable -> load -> resume` 后主节点与 alias 立即交叉读写场景。

### 边界

当前 devtmpfs 不支持 primary node 与 alias 的跨目录项批量原子发布。主节点出现前，alias 可被 `lstat()` 观察为悬空链接；它不能被正常 path follow、open、mount 或 I/O 使用。

## 2. 首次 load/resume 生命周期向 Linux 对齐

### 背景

在本机 Linux 对 tableless `wdf` 做 `create --notable -> load -> resume` 分阶段实测后，确认 Linux 的用户态顺序不是 alias-first：首次 load 返回前 `/dev/dm-X` 已创建，而 mapper 仍只有 inactive table；primary 可 open，但 `BLKGETSIZE64` 为 0、read 为 EOF，`/dev/mapper/<name>` 尚不存在。首次 resume 返回前 alias 才创建，active table 容量和实际 I/O 随之可用。

### 改动

- mapper runtime 注册拆分为 `register_mapper_primary()` 与 `publish_mapper_alias()`：首个成功 table load 注册 primary node、Live block registry 与 accepting `BlockFile`；首次 resume 只用 `InitialResumeGuard` 激活 table 并发布 alias。
- `DmDevice::metadata()` 和 `OpenBlockFile::read_at()` 复用既有 active-table 容量逻辑：Loaded-inactive primary 容量为 0、read EOF，inactive table 不承接 BIO。
- 首次 load 的 primary 注册在 table 完整解析/校验后、写入 inactive 前执行；注册失败不改变 table 或 readonly。
- primary-only 状态下 rename 仅改变 manager/device 名称，之后 resume 以新名称发布 alias；remove 可在无 alias 时撤销 primary runtime。
- core ktest 的 table parser/state 测试显式绕过 runtime devtmpfs，因为该环境未挂载 runtime devtmpfs；真实 primary node 语义由 NixOS control-plane guest 覆盖。
