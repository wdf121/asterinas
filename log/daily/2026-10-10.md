## 4. 排查并修复内核构建串用 main 基线目录的 OSDK

### 背景

用户运行 `make kernel` 遇到 align_ext 0.1.0 的 lockfile package collision：依赖同时来自 `/root/asterinas` 与 `/root/main-baseline-7cf6fb02d`。只读排查确认这是构建工具的源码路径绑定串用，不能归类为 rebase 合坏内核源码。

### 根因与处理

- 容器 Cargo 安装元数据表明，默认 cargo-osdk 来自 `path+file:///root/main-baseline-7cf6fb02d/osdk`；二进制包含该基线路径，不包含当前 `/root/asterinas/osdk` 路径。

- worktree 隔离没有覆盖容器共享的 `/root/.cargo/bin`。Makefile 的工具自动更新依赖时间戳，不核对安装来源；clippy/udeps 转发路径不生成同样的内核包装清单，因此完整 `make check` 通过不能排除此问题。

- 本次不修改内核源码，不手工删除锁文件或全量清理 target；通过重新安装正确来源的工具，让 OSDK 按现有逻辑重新生成包装清单。

## 6. ext2 落盘空闲块计数不一致修复

### 背景

新建 release NixOS 根盘启动前 `e2fsck -fn` 返回 0，正常登录、账户检查、`sync` 并 `poweroff` 后检查返回 4，唯一报告为块组 0 空闲块计数 `19315` 与位图统计 `19314` 不符。先补最小定向 ktest 复现，再修复。

### 根因与改动

- `kernel/core/src/fs/fs_impls/ext2/block_group.rs`：`sync_metadata` 改为 `pub(super)` 供 `fs.rs` 最终元数据遍历调用。
- `kernel/core/src/fs/fs_impls/ext2/fs.rs`：原 `sync_all` 在逐组同步后直接持久化计数，但 inode 写回可能在其后改变其它组的分配状态。修复为最终元数据遍历持有超级块写锁冻结分配，在锁内刷新各组位图与描述符快照后统一持久化计数，且该阶段不再触发会自行分配块的 inode 同步。
- `kernel/core/src/fs/fs_impls/ext2/test_utils.rs`：新增 `assert_disk_free_counts`（按落盘字节统计位图实际空闲位并对照持久化计数，不信任缓存）、可注入指定块写失败的 `fail_writes_to`、`with_bitmap_counts` 构造项；新增 4 个确定性用例：分配/释放后同步、延迟分配、延迟释放、写失败后重试同步。

### 验证

- 同一新增用例先失败后通过：修复前 `14 passed; 1 failed`、`12 passed; 2 failed`（红阶段），修复后 ext2 模块 ktest `15 passed; 0 failed; 224 filtered`（绿）。
- NixOS release 根盘端到端复验通过：启动前 `e2fsck -fn` 0 → 正常登录与账户检查通过 → 有序关机退出 0 → 重启后 `e2fsck -fn` 0（postboot e2fsck 0）。
- 复验期间 ext2 mount lease ktest 1/0 顺带复跑通过；故障盘备份 `target/nixos/failed-root-MdBL2F/`、修复前镜像 `target/nixos/pre-ext2-fix-OEsCVh/` 保留。

## 8. DM_LIST_DEVICES 支持 DM_UUID_FLAG

### 背景与改动

`kernel/core/src/device/misc/device_mapper.rs`：`DM_UUID_FLAG` 原先只允许 `DM_DEV_RENAME_CMD` 使用，其余命令返回 `EINVAL`，导致真实 LVM2 的 `dmsetup ls --uuid` 类查询失败（`--linear-integration` 首层失败原因）。放宽为 `DM_DEV_RENAME_CMD` 与 `DM_LIST_DEVICES_CMD` 均可携带；`DM_LIST_DEVICES_CMD` 按 `DM_UUID_FLAG` 输出两种记录布局：无标志时为 8 字节对齐的紧凑 `dev | next | name\0` 形式，有标志时为带 event number、name-list flags 与可选 UUID 的扩展形式。

### 验证

当日 `--linear-integration` 仍因 sysfs 第二层根因失败（见 10-12 日志第 1 节）；本修复的正确性由 10-12 的 `--linear-integration` 全套通过覆盖验证。
