# 2026-9-11 Device Mapper 进度

## P2.1 runtime rename 资源事务

- 运行中 mapper rename 原先先更新 `DmManager` 的 name/UUID index 与 `DmDevice.name`，再改 `/dev/mapper/<name>` alias；若 alias 操作失败，再反向更新 index。P1.4 移除全局控制锁后，该窗口允许并发 create 抢占旧 name，使反向回滚失败并遗留 index/alias 分裂。
- `DmManager` 新增 runtime rename name reservation：rename 持有 mapper lifecycle guard 时，旧 name 继续映射原设备，新 name 预留为不可 create/rename；alias 操作不持 manager lock。alias 成功后一次提交 name index、UUID index 和 `DmDevice.name`；失败时 reservation drop，只释放新 name，旧状态不变。
- 这样不需要在 alias 失败后执行可能失败的反向 index rollback，也不会因 devtmpfs rename 阻塞无关 mapper 的 manager 操作。该阶段不承诺 devtmpfs alias 与 control index 跨命名空间的瞬时全局原子可见性，只保证操作完成后不存在持久资源分裂。

## P2.2 首次 primary 发布失败原子性

- `register_runtime_primary()` 原先先将 block registration 提交为 Live 并开放 wrapper open gate，再创建 `/dev/dm-N`。若 node 创建失败，撤销 Live registration 可能被 open 或 lease 阻塞，失败 ioctl 会遗留无 node 的 registry/wrapper。
- 调整顺序为 pending registration → pending wrapper（拒绝 open）→ 创建 primary node → block registration 变 Live → 记录 node → 开放 open gate。node 创建失败时只清除 pending wrapper 并 abort pending registration；`DM_TABLE_LOAD` 尚未安装 inactive table。
- ktest 注入 node creator `EIO`：block registry/wrapper lookup 均无残留、同一 `DeviceId` 可再次 pending-register；ioctl 入口返回 `EIO` 时 active/inactive table、event、readonly 均保持初始状态。

## P2.3 remove 回滚隔离与重试

- runtime remove 原先在 primary 删除失败后尝试恢复 alias，或 unregister commit 失败后恢复 primary/alias；恢复失败仅 `warn!`，unregistration token 析构会恢复 Live registry/open gate，可能让缺失 runtime node 的 mapper 继续被 lookup/open。
- `PendingBlockDeviceUnregistration` 增加显式保留 `Removing` 的 RAII 状态；`BlockFile` 保存无法完整补偿的 token。恢复失败返回 `EIO`，registry lookup/lease 继续隐藏、wrapper open 返回 `ENODEV`；同名 remove 可取回 token 并继续提交注销。
- 注入 primary 删除 `EIO` 与 alias restore `EIO` 的双失败 ktest 通过：设备进入隔离状态，随后重试 `commit_unregister` 成功。另有隔离 token 与正常 remove/remove_all control-plane 回归。
