# 2026-W38：Device Mapper 控制面调试训练

> 周期：2026-09-14 至 2026-09-20
>
> 本周以命令驱动的控制面学习为主；默认先使用 `LOG_LEVEL=error` 可见的低频 `[dm-debug]` 控制面诊断日志打通主链，日志不足时再用 `strace`，仅在两者仍无法解释原始 ABI、实际分支或并发状态时使用 GDB。不恢复第三版生产优化、不修复已发现的 `wait` 异常、不进入复杂 target、backing remap 或 LVM 编排。

## 1. 本周目标

建立稳定的三层学习闭环：

```text
第一层：业务逻辑
用户要什么、前置状态是什么
→ 成功、失败后用户应看到什么

第二层：代码主逻辑
核心 ioctl / handler / workflow
→ 数据来源、ABI 编解码、状态转换、结果回写与 userspace 消费

第三层：正确性边界
资源生命周期与所有权
→ 并发访问者、锁粒度与锁顺序
→ 数据竞争、死锁、失败回滚、容量与状态边界
→ 正常、失败、并发场景的验证证据
```

每层按成本升级运行证据：`[dm-debug]` `ostd::error!` → `strace` → 仅在仍有关键事实不明时使用 GDB。

本周不追求覆盖大量 `dmsetup` 子命令，而是完成三种不同的控制面形态：**可变长列表输出、mapper 状态转换、事件等待**。

## 2. 已完成基线

### `dmsetup version`

已完成用户态 `strace` 与内核侧 GDB 的首个闭环：

```text
Library version 由用户态 libdevmapper 输出
→ /dev/mapper/control 上两次 DM_VERSION
→ syscall_dispatch → sys_ioctl → inode_handle::ioctl
→ DmControlFile::ioctl
→ 内核回写 driver version 4.48.0
```

本周不重复展开其所有辅助函数。若需回顾，以 [GDB 学习笔记](../../todo/gdb.md) 中的已确认记录为准。

## 3. 本周练习顺序

| 优先级 | 命令/主题 | 本周要完成的事 | 完成证据 |
|---:|---|---|---|
| 1 | `dmsetup targets` | 先说明“列出当前内核支持 target 能力”的用户语义；再沿 `DM_LIST_VERSIONS` 的静态 metadata → 可变长 target-version record → userspace 解析链路解释代码；最后检查 record 容量、`next` 回填、8 字节对齐与 buffer-full 边界。 | `[dm-debug]` record 摘要与 CLI 输出对应；能从 `data_start` 解释至少一条实际 record 的 `next`、版本号与名称；仅在需要核对原始字节时使用 GDB。 |
| 2 | zero mapper 生命周期 + `dmsetup info` | 先走通 `create --notable → load → resume → suspend → clear/remove` 的业务状态变化；再解释 ioctl/workflow/core 状态提交与 `info`；最后检查 mapper/table/runtime node/alias/event 的资源所有权、发布/回收、lifecycle guard、失败与并发边界。 | 能用 CLI 与 `[dm-debug]` 解释每个状态点；能说明 active/inactive、primary/alias、event 的提交顺序、锁/并发边界和至少一个失败或拒绝路径。 |
| 3 | `dmsetup wait` | 先建立 event number 的业务语义：旧 event 为何应立即返回、当前 event 为何应等待；再沿 wait 请求、event 发布与控制面分派缩小代码路径；最后分析 waiter、event queue、lifecycle/manager 状态与当前异常路径的并发和回滚边界。 | 能先用日志与 CLI 复现并说明异常；需要时以 `strace`、GDB 提供实际边界/分派证据，但本周不修复。 |

### 3.1 生命周期练习的观察点

zero target 的价值是排除 backing device、lease、sector remap 和真实 I/O 布局等变量，把注意力集中在控制面状态机。

```text
create --notable
→ 是否已有 mapper identity？是否已有 runtime node？

load zero table
→ inactive table 是否存在？primary node、容量和 alias 分别如何变化？

resume
→ inactive 如何切换为 active？何时出现 /dev/mapper/<name>？

suspend / clear / remove
→ 哪个状态可转换、哪个状态应拒绝？event 和节点如何变化？
```

每个状态点先由学习者根据前一步命令推断，再用 `dmsetup info`、`table` 或节点观察验证。`table` 在本周只作为生命周期的辅助观察，暂不单独展开其 active/inactive selector 和完整输出 ABI。

### 3.2 `[dm-debug]` 低频控制面观察

本周增加的本地学习通道仅在 `LOG_LEVEL=error` 下输出带 `[dm-debug]` 前缀的控制面与生命周期摘要；它不是 upstream 日志严重性策略，也不记录数据面每 BIO。

- 每个成功解码的 ioctl 依次输出 `ioctl begin`、header 摘要、`ioctl done`；header 只含稳定命令名、raw ioctl、name/dev、flags、target count、data size/start，不含 UUID、userspace buffer 指针或 table 参数。
- `DM_LIST_VERSIONS` 只在一条 target-version record 完整编码且其 `next` 最终确定后输出 `offset/next/version/name/record_len`；循环结束输出 `records` 与 `buffer_full`。`DM_GET_TARGET_VERSION` 仅在成功编码时输出一条 `next=0` 摘要，不 dump 原始字节或 padding。
- create/load/resume/suspend/remove 保留具有 ABI 或跨资源价值的控制提交摘要；DM core 只输出 inactive/active table、phase、event 和 postponed BIO 的真实状态提交。`DM_TABLE_CLEAR` 不再输出与 core 重复的 control 行，改由 core `state table-cleared` 的 `cleared` 字段说明结果。
- `dmsetup` 可能先由 libdevmapper 发送 `DM_VERSION`。2026-09-15 实测：`dmsetup targets` 对应 `DM_VERSION → DM_LIST_VERSIONS`，随后输出 error、linear、striped、zero 四条最终 record，offset 从 312 起、前三条 `next=24`、最后一条 `next=0`；zero mapper 的 `create --notable → load → resume` 分别出现 create、带 target 数/readonly 的 table-load、initial-resume 的日志。
- zero mapper 的 Read/Write 在 marker 区间内未出现 `[dm-debug]`，确认本通道未进入 `enqueue`、target map、BIO split/completion 或 flush fan-out。
- 预期的未知 mapper 查询仍显示一组 ioctl begin/header/done，done 为 `ENXIO`；不额外输出完整 registry 或第二套预期错误日志。

学习时在 guest shell 用 marker 关联 CLI 与内核输出：

```bash
printf 'DM_CMD_BEGIN targets\n'
dmsetup targets
printf 'DM_CMD_END targets\n'
```

`DM_DEV_WAIT` 不属于本次日志任务：它目前可显示入口日志，但仍在现有 dispatch 异常处中断，不将其当作 wait 已可完成的证据。

## 4. 为什么暂不进入 LVM

LVM 是多层用户态编排，而不是单个 DM ioctl 的同义词：

```text
pvcreate / vgcreate / lvcreate
→ 扫描与元数据操作
→ 多次块设备 ioctl
→ 多次 Device Mapper 控制命令
→ 可能伴随 udev 相关兼容行为
```

在能够独立解释 `create/load/resume` 前进入 LVM，会难以区分“LVM 自己的操作”与“LVM 经由 DM 发起的操作”。

下周优先顺序预留为：

```text
linear target
→ dmsetup table / deps
→ dd 验证最小数据面 remap
→ 最小 LVM：pvcreate → vgcreate → lvcreate
```

届时 `table`、`deps`、backing device 和 LVM 自动生成的 mapper 才会形成一条可解释的完整链路。

## 5. 每项练习的执行规则

1. **业务逻辑优先**：先说用户要什么、前置状态是什么、成功/失败后应看见什么；
2. **再走代码主逻辑**：从命令反推核心 ioctl、handler/workflow、数据来源、ABI 编解码、状态转换、结果回写与 userspace 消费；
3. **最后补全正确性边界**：明确资源的创建/发布/回收、并发访问者、锁粒度和锁顺序、数据竞争/死锁风险、失败回滚、容量与非法输入边界；
4. **运行证据按需升级**：先用 `[dm-debug]` 日志关联 CLI；日志不能解释 userspace/内核边界时用 `strace`；只有 ABI 原始字段、真实分支或并发状态仍不明确时才进入 GDB；
5. 由学习者运行命令、观察并先判断；不把源码推断、历史 trace 或既有日志当作本次已证实事实；
6. 确认一个命令的三层闭环后，才更新 `todo/strace.md` 或 `todo/gdb.md`。
